# rag-knowledge-base

私有化部署的企业知识库 RAG 引擎：**文档解析与向量化全部在本机完成，原文不出内网**；只有「检索到的少数片段」会被发给云端大模型生成答案。

面向的场景是内部制度问答——员工手册、考勤、报销、信息安全规范这类文档。它不追求通用聊天，只做一件事：**在你自己的一堆文件里找到依据，带着出处回答，找不到就说找不到**。

## 30 秒跑起来

不需要 GPU、不需要 Ollama、不需要外部 API Key，仓库自带 5 篇示例制度文档，装完依赖就能入库并提问。

> 首次 `ingest` 会上网下载约 640MB 的本地向量模型（到 `data/models/`），具体耗时看网络。模型缓存之后这几条命令总共十几秒。卡在下载、下载完却降级成 hash、Windows 上磁盘多占一份——见[常见问题](#常见问题)。

```bash
python -m venv .venv
.venv\Scripts\activate            # Windows
source .venv/bin/activate         # macOS / Linux

pip install -r requirements.txt
python -m app.cli ingest ./demo-docs
python -m app.cli serve --host 127.0.0.1 --port 8080
```

打开 `http://127.0.0.1:8080`。完整步骤（`.env` 与 API Key、首次登录口令、Windows 注意事项）见[快速开始](#快速开始)。

## 特性

- **零外部依赖，clone 完就能跑**：不需要 GPU、不需要 Ollama、不需要 torch，也不配外部 API Key 就能把整条链路跑起来（没 Key 时自动降级为离线摘录模式）。内置 5 篇示例制度文档，`ingest` 完立刻可问。
- **本地向量化，原文不出内网**：`fastembed` + ONNX Runtime 在本机 CPU 上算向量，文档解析与向量化都在本机完成。只有命中的少数片段会被拼进 Prompt 外发。
- **混合检索：关键词 + 语义双路召回**：BM25 负责「年假天数」「报销时限」这类字面精确命中，向量路负责「年假没休完能留到明年吗」这类同义表述；两路用 RRF 融合，避免任何一路的盲区直接变成答不出来。
- **父子块切分**：检索用小块保精度，喂给模型的是它所属的父块，保证答案上下文完整（细节见[技术要点](#技术要点)）。
- **拒答机制**：**配了 API Key 时两道防线都在**——检索相关度低于阈值直接返回兜底答复，同域但文档没写的问题则由生成层判定兜底；被拒的问题会记进「未答清单」，这份清单就是补文档的待办列表。**离线摘录模式只有第一道**（阈值），见[常见问题](#常见问题)。
- **引用溯源**：答案里每条结论标注 `[1] [2]`，接口同时返回每个编号对应的文档标题、章节路径、片段。编号来自本次真实检索结果，模型编造的编号会被过滤掉。问答页把这次召回的**全部**依据列成可展开的「检索依据」列表，被引用的标「已引用」——列了 6 条而正文只标 `[1] [2]` 是正常的，见[界面](#界面)。
- **PII 脱敏**：片段外发前正则过滤手机号、身份证号、邮箱、银行卡号。员工手册里常有这些，直接发给云端就是合规事故。
- **多用户隔离**：账号由管理员统一发放（不开放注册），会话按账号隔离，访问他人 `conversation_id` 返回 404 而不是 403——不泄露会话是否存在。
- **多轮追问**：只对含指代词（「这个」「上述」「第 3 步」）或「那…呢」这类省略式追问，才触发一次小模型调用；其余问题原样检索，不猜也不改写。改写**只补主语**——不得引入上一轮回答里的事实、数字、日期，改写成是非问会被直接拒绝并回退原问题。离线摘录模式没有生成能力，不做改写。
- **错别字与同义词兜底**：确定性纠错词表 + 阈值触发的模型纠错；领域同义词扩展只作用于 BM25（补「用户怎么说」与「文档怎么写」之间的词面鸿沟）。
- **内置评测集与脚本**：`eval/` 下有黄金测试集和 Recall@k / MRR / 拒答准确率 / P95 延迟的执行脚本，改参数后能立刻知道是变好还是变差。

## 架构

### 入库（一次性，或每次文档更新后增量执行）

```
 你的文档                扫描与解析                        切分                     存储
┌──────────┐    ┌────────────────────┐    ┌────────────────────────┐   ┌──────────────────────┐
│ .md .txt │    │ scan_dir           │    │ 按 # 标题切章节         │   │ Chroma               │
│ .csv     │───▶│  支持的进队列       │───▶│   └─ 父块 ≤2200 字      │──▶│  只存子块向量         │
│ .docx    │    │  不支持的单列报告   │    │        └─ 子块 ≤700 字  │   │  data/chroma         │
│ .pptx    │    │ load_file          │    │           （重叠 120）  │   ├──────────────────────┤
│ .xlsx    │    │  统一成带标题的文本 │    │                        │   │ SQLite registry.db   │
│ .pdf     │    │  PDF 去页眉页脚/OCR │    │ 子块向量化（本地 ONNX） │   │  文档/父块/子块/会话  │
│ .html    │    └────────────────────┘    └────────────────────────┘   ├──────────────────────┤
│ 图片(OCR)│                                                            │ BM25 索引 bm25_*.pkl │
└──────────┘                                                            └──────────────────────┘
```

增量语义：mtime 未变的文件直接跳过（不读盘）；内容哈希未变的只刷新 mtime；内容完全重复的副本只留一份；单文件失败不影响整批，错误全部回收进入库报告。

### 一次问答（`RagEngine.answer()` 的真实顺序）

```
用户问题
  │
  ├─[1] 取会话历史（按 username + conversation_id；非本人会话 → 404）
  ├─[2] 追问改写：只在命中指代词或「那…呢」时调一次模型；离线模式不懂指代，直接按原问题检索（不拼接上一问）
  ├─[3] 错别字纠错：先查确定性词表；检索分仍低于 correct_trigger_score 时让模型纠一次，重检提升 >0.05 才采纳
  ├─[4] 双路召回
  │      ├─ 向量路：问题 → 本地 embedding → Chroma top-N（dense_top_k）
  │      └─ 关键词路：领域同义词扩展 → jieba 分词 → BM25 top-N（sparse_top_k）
  ├─[5] RRF 融合：只看排名，score = Σ w /(rrf_k + rank + 1)，取 fusion_k 条
  ├─[6] 单文档限流（max_per_doc）→ 重排（默认 none）→ final_top_k 条
  ├─[7] 拒答闸门：best_dense < min_top_score → 直接回兜底答复，记入未答清单，结束
  ├─[8] 父块补全：命中子块换回父块，同一父块只留一次，按去重后块数均分 max_context_chars
  ├─[9] PII 脱敏（手机号 / 身份证 / 邮箱 / 银行卡）
  ├─[10] 云端 LLM（OpenAI 兼容协议；调用失败或返回空 → 本地「原文摘录」兜底，不抛 500）
  └─[11] 判定（NO_ANSWER 标记 / 无引用降级提示）→ 落库（会话轮次 + 未答清单）→ 返回
```

流式接口 `/chat/stream` 走的是同一套闸门：阈值、拒答判定、引用校验、落库逻辑与同步接口完全一致，只是文本边生成边推。所以「问答页上看到的」和「接口返回的」不会出现两套结果。

## 快速开始

前置：Python 3.10+（开发与测试在 3.13 上进行，其余版本未逐一验证）；磁盘预留 3GB 以上——`requirements.txt` 里的大包（`chromadb`、`fastembed`、`opencv`、`pymupdf`）本身就不小，再加上首次下载约 640MB 的 embedding 模型，以及入库后生成的向量库与索引（Windows 上模型目录会额外多占一份，原因见[常见问题](#常见问题)）。

```bash
git clone <仓库地址>
cd rag-knowledge-base

python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS / Linux:
source .venv/bin/activate

pip install -r requirements.txt

# 复制配置模板（Windows 用 copy .env.example .env）
cp .env.example .env
# 然后编辑 .env，把 LLM_API_KEY 填成你自己的 key

python -m app.cli ingest ./demo-docs
python -m app.cli serve --host 127.0.0.1 --port 8080
```

打开 `http://127.0.0.1:8080`。

几点必须知道的：

1. **所有命令都在项目根目录执行**。`data/`、`./demo-docs`、`./data/chroma` 这些相对路径都以当前工作目录为基准。
2. **第一次点「登录」时，终端才会打印管理员初始口令**。账号库是懒创建的：`data/auth.json` 在第一次真正需要校验账号时才生成（也就是第一次提交登录表单那一下），同时输出
   `[auth] 初始化管理员账号 admin，初始密码：xxxxxxxx（请登录后立即修改）`
   所以第一次登录大概率会因为不知道密码而失败——这不是故障。**回到终端看那行口令，用 `admin` + 该口令再登录一次**，进去第一件事是改密码。
   口令**只打印这一次**。如果关了终端丢了它，删除 `data/auth.json` 并重启服务即可重新生成（代价是已有账号全部丢失）。
3. **`pip install` 比较慢**，`chromadb` / `fastembed` / `opencv` / `pymupdf` 都是大包。首次 `ingest` 还会下载 embedding 模型到 `data/models/`（约 640MB），之后完全离线。代码里对 HuggingFace 端点做了 `setdefault("HF_ENDPOINT", "https://hf-mirror.com")`，境外网络可自行覆盖该环境变量。
4. **没有 API Key 也能跑通全链路**。此时云端模型返回 401，引擎自动降级为「离线摘录模式」：不生成答案，只从命中片段里抽出最相关的原文句子并标注出处。用来验证入库和检索够用，但回答是拼接的，不是整合过的。
5. 服务默认只监听 `127.0.0.1`，**局域网内其他机器访问不到**。要对外提供服务请改监听地址并放在 Nginx 之类的前置代理之后，别把内部服务端口直接暴露到公网。

入库成功时终端输出长这样（`demo-docs/` 在默认配置下的真实输出，只有 `耗时` 用 `X.XXs` 代替）：

```
新增 5 / 更新 0 / 跳过 0 / 失败 0
本次写入 59 个 chunk；库内共 5 篇文档、59 个 chunk；耗时 X.XXs
```

`耗时` 取决于机器和是否首次运行：首次要下载模型并跑 ONNX 推理，明显更慢；之后有向量缓存会快不少。`chunk` 数由 `chunking` 的 `max_chars` / `parent_max_chars` 决定，改了分块参数这个数就会变。

**入库日志里如果出现「降级为 hash 向量」，先别调检索参数**：那是 embedding 模型没加载成功（多为内存不足），此后分数接近 0、排序随机，但接口不报错。处理办法见[常见问题](#常见问题)。

不想手敲命令的话，`scripts/` 下有两个脚本：`scripts/ingest_demo.sh`（入库示例文档）、`scripts/run_server.sh`（启动服务）。**Windows 用户请用对应的 `.bat`**：`scripts\ingest_demo.bat`、`scripts\run_server.bat`（双击即可）；`scripts\*.sh` 在 Git Bash 里也能用，脚本会依次找 `.venv/bin/python` 和 `.venv/Scripts/python.exe`。四个脚本都优先使用项目内 `.venv`，找不到才回退到系统 `python`，并且会先自检 `chromadb` / `fastembed` 是否装在这个解释器里——没装就明确报错让你先激活虚拟环境，而不是抛一堆 ImportError 让你以为依赖装错了。脚本可以从任意目录调用。依赖装在别的环境里（而不是项目里的 `.venv`）时，用 `RAG_PYTHON` 直接指定解释器，优先于自动探测：`RAG_PYTHON=/path/to/python ./scripts/run_server.sh`，Windows 下 `set RAG_PYTHON=C:\path\to\python.exe`。

`新增` / `更新` / `跳过` / `失败` 之外，还有两类**不算失败但意味着知识库少了内容**的情况会单独列出：`格式不支持，未入库` 和 `读到了但没有可用文本`。这两个列表不要忽略，知识库「莫名缺内容」大多出在这里。

## 界面

打开 `http://127.0.0.1:8080` 只有一页：左栏是「新对话」按钮 +「高频场景」「知识库分类」和按时段（今天 / 昨天 / 更早）分组的历史会话，中间是问答区。分类树里的每个叶子点一下，就是拿这个分类名当问题发出去——问出来的东西莫名其妙时，先确认它到底问了什么。

答案卡片从上到下是：结论句 → 分条规则 → 补充说明 → **检索依据** → 复制 / 生成规范答复 / 收藏。

### 「检索依据（N 条）」

每条回答末尾都有一个**默认收起**的折叠块，标题带条数。下面是一次真实运行（问「年假多少天」，本次召回 6 条，中间几条省略）：

```
检索依据（6 条）
 1  员工手册（2026 版）    第三章 年假与休假 > 3.2 年假申请流程   已引用   相关度 59%
    ▸ 原始片段
 2  员工手册（2026 版）    第三章 年假与休假 > 3.1 年假天数       已引用   相关度 67%
    ▸ 原始片段
 3  考勤与请假管理办法    3 审批流程 > 3.1 审批权限                        相关度 36%
 ...
 6  差旅与费用报销制度    3 报销流程与时限 > 3.2 报销步骤                  相关度 23%
```

每一行是：序号、文档标题、章节路径、被正文引用时的「已引用」标记、相关度百分比；该条带 `snippet` 时，下面还套一层可展开的「原始片段」。三种交互各管一件事：

- **点某一行** → 右侧抽屉打开这一条的原文（`snippet`，缺失时回落到 `text`）。列表管「这次一共召回了哪些」，抽屉管「这一条到底长什么样」。
- **点正文里的 `[n]` 胶囊** → 自动展开折叠块、滚到第 n 条、高亮约 1.6 秒，并把它下面的「原始片段」一起展开。不用自己去列表里找编号。
- **从历史对话回放的旧回答**没有 `sources`，此时点胶囊直接开抽屉——不会点了没反应。

### 为什么列了 6 条，正文只标了 `[1] [2]`

`sources[]` 是本次检索的**全部召回**（`retrieval.final_top_k`，默认 6），正文里的 `[n]` 只是这次真正被用到的几条。

「被引用」和「召回了但没用上」都是信息：前者说明答案有依据，后者说明库里确实有相关内容、只是没进最终答复——判断该不该补文档、该不该调查分块参数时，看的就是这个差集。

「已引用」标记取的是**正文实际渲染出的 `[n]` ∪ `flags.citations`**，不是照抄某个字段。取并集是为了让列表标记和你屏幕上的胶囊一一对应，不会出现「列表说引用了、正文里找不到那个编号」的情况。

### 「相关度」这个百分比是什么

就是 `dense_score`（向量余弦相似度，0~1）四舍五入到整数，**不是** `score`。融合分上界约 `2/61≈0.033`，做成百分比会显示成「相关度 3%」，所以界面上完全不出现它。两个字段的区别见[技术要点](#技术要点)①。

`dense_score` 缺失、或这一条只从 BM25 路命中（值为 `0`）时，整个标签不显示，而不是显示「相关度 0%」——后者会被读成「一点都不像」，实际情况是「没有语义分可比」。

### 顺序不是相关度降序

上面那张表里第 1 条 59%、第 2 条 67%，不是排序错了。列表顺序是两路各自排名 → RRF 融合 → 精排之后的结果，`dense_score` 只是其中一路的依据：第 1 条在 BM25 路也排得靠前，融合后名次更高。所以**别拿百分比去反推排序逻辑**，详见[技术要点](#技术要点)①。

## 命令行

```
python -m app.cli ingest <目录或单文件> [--reset] [--force]   导入 / 增量更新
python -m app.cli ask "问题" [-c 会话ID] [--json]             提问并打印出处
python -m app.cli search "问题" [-k 6]                        只看检索结果，不调模型（调参必备）
python -m app.cli stats                                       文档数 / chunk 数 / 向量数 / BM25 条数
python -m app.cli unanswered [--limit 30]                     被拒答的问题清单（知识盲区）
python -m app.cli serve [--host 127.0.0.1] [--port 8080] [--reload]   启动 HTTP 服务
```

`--config` 可放在子命令前指定另一个配置文件：`python -m app.cli --config ./config.test.yaml ingest ./demo-docs`。

`search` 的输出是调参的主要依据：

```
best_dense=0.6313  命中 6 条
1. [员工手册（2026 版） / 第三章 年假与休假 > 3.2 年假申请流程] rrf=0.0325 dense=0.568 bm25=17.58
   年假需提前 3 个工作日在 OA 系统「请假申请」中提交，由直属主管审批；连续休假超过 5 天的，需部门负责人二次审批。年假期间工资照常发放。…
```

（`demo-docs/` + 默认 `fastembed` 模型的真实输出。每条命中下面还有一行片段摘要，这里只保留了前两条。）

注意第 1 名和第 2 名的 `dense` 与 `bm25` 排名正好相反：BM25 被「年假」的字面频次拉到 17.58，向量路更认语义（`dense=0.631` 是全场最高）。两条都会进上下文（父块补全后按块去重），所以答案不受这个排序影响；但这正是需要两路的原因——只看 BM25 容易答成「申请流程」，只看向量又会漏掉「提前 3 个工作日」这类字面条款。

`dense` 是向量余弦相似度，`bm25` 是关键词得分，`rrf` 是两者的排名融合分——**`rrf` 不是相似度，不要拿它跟 0.6、0.8 比**：同一行里 `dense=0.568` 与 `rrf=0.0325` 差两个数量级，就是这个意思（原因见技术要点）。拒答阈值比的是 `best_dense`。

单机内网调试用，默认只监听本机。

|---|---|---|

| POST | `/login` | 账号密码登录，成功后种 7 天有效的 HttpOnly Cookie |
| GET | `/health` | 服务与知识库状态，**需要登录**（无 Cookie / Bearer Token 返回 401） |
| POST | `/chat` | 同步问答，返回 `text` + `sources` + `conclusion/rules/notes` |
| POST | `/chat/stream` | SSE 流式问答，事件序列 `meta → sources → delta* → done` |
| POST | `/search` | 只检索不生成 |
| GET | `/conversations`、`/conversations/{id}` | 当前账号的历史会话 |
| GET | `/unanswered` | 未答问题清单（需管理员） |
| — | `/admin/*` | 账号管理、文档增删、分类树、入库报告、调用量统计（需管理员） |

`/health` 返回的是业务状态而不是裸探针，因此和其它业务接口一样需要登录态，用外部监控采集请带上 Token；如果只是想在 CI 或部署脚本里判断进程活没活，直接用 `curl -sf http://127.0.0.1:8080/` 更省事。

`/chat` 的 `sources[]` 里有两个分数，别混用：**`dense_score` 是向量余弦相似度**（0~1，语义稳定，界面上的「相关度」用它）；**`score` 是 RRF 排名融合分**（`rrf_k=60`、两路权重都是 1.0 时上界约 2/61≈0.033），一旦把 `rerank.provider` 开成 `cross_encoder`，`score` 又会变成 rerank 分值、量纲再变一次，所以它只适合排查排序，不适合当相似度展示、也不要拿去跟 0.6 比。

`/search` 返回的每个 `hit` 是 `score` / `dense` / `bm25` 三个并列字段（对应 CLI `search` 打印的 `rrf=` / `dense=` / `bm25=`）。这里的 **`dense` 与 `/chat` sources 的 `dense_score` 是同一个指标，只是字段名不同**：`/search` 是排查用接口，三个短名成组出现、语境自明；`/chat` 的 `sources` 是对外契约，字段名要能独立看懂，所以叫 `dense_score`。

配置在 `config.yaml`，支持 `${VAR}` 与 `${VAR:-默认值}` 两种环境变量插值，所以 API Key 不需要写进文件。`.env` 由配置层自己加载（固定读项目根目录的 `.env`，不依赖工作目录）。

|---|---|---|
| `app.name` | 见 `config.yaml` | 会写进系统提示词，是回答里的自称。改成你自己的公司名或部门名 |
| `app.data_dir` | `./data` | 索引、向量库、账号库、BM25 全在这里。换目录等于换一套独立知识库，可用来隔离测试环境 |

| `embedding.provider` | `fastembed` | 本地 ONNX 推理。初始化失败会**自动降级为 hash 向量**（日志有 WARNING），此时召回质量不可用，务必先修这里 |

| `embedding.batch_size` | `64` | 调大快点但更吃内存；CPU 机器上 32~64 是安全区 |
| `embedding.cache` | `true` | 按段落哈希缓存向量。增量入库必开，重跑全库时能省掉绝大部分计算 |
| `vector_store.provider` | `chroma` | `memory` 仅供测试，进程退出数据即丢 |
| `llm.provider` / `base_url` / `model` | `openai_compat` / DeepSeek / `deepseek-v4-flash` | 任何 OpenAI 兼容端点都能用（DeepSeek、通义、混元、vLLM、One-API、Ollama 的 OpenAI 模式）。改成 `extractive` 即完全离线，代价是回答退化为摘录 |
| `llm.api_key` | `${LLM_API_KEY:-}` | 从环境变量取，不要写死 |
| `llm.max_tokens` | `2048` | 推理模型的「思考」和「答案」共用这个预算。给到 1200 以下时思考可能吃光预算、正文字段为空，引擎会判定失败并走摘录兜底。它只作用于生成答案：追问改写 / 纠错 / LLM 精排的预算在代码里各自写死（512 / 512 / 1024），同一个道理——给小了正文返回空，调用方只会静默回退，日志前缀分别是 `[rewrite] 改写未生效:` `[correct] 纠错未生效:` `[rerank] 重排未生效:` |
| `llm.temperature` | `0.1` | 制度问答要稳。调高会让措辞飘，数字和期限反而更容易被改写 |
| `retrieval.final_top_k` | `6` | 最终喂给模型的片段数。调大覆盖更全但更慢更贵，噪声也更多；调小容易漏掉关键条款 |

| `retrieval.max_context_chars` | `6000` | 上下文总预算，按「去重后的实际块数」均分，不是按命中数均分。总需求不超预算时不截断 |

| `retrieval.use_parent_context` | `true` | 命中子块时换回父块喂模型。关掉后上下文更短更省 token，但答案容易缺前提条件 |

| `conversation.max_turns` / `history_turns_for_llm` / `rewrite` | `6` / `3` / `true` | 保留几轮历史、真正送给模型几轮、是否开启追问改写。**标定 `min_top_score` 或跑召回评测时必须把它设成 `false`**：改写后的查询把主语补全了，`dense` 天然比原句高 0.15 以上，拿它标出来的阈值不可比 |
| `guard.redact_pii` / `require_citation` | `true` / `true` | 外发前脱敏；没有引用就降级为「未标注出处」提示。除非你在做对比实验，不要关 |

## 换成自己的文档

1. 把文件放进一个目录（可以多级子目录，`demo-docs/` 就是范例），删掉或保留示例文档都行。
2. 执行 `python -m app.cli ingest ./你的目录`。
3. 想清空重来加 `--reset`；改了文件但 mtime 没变（比如从备份还原）加 `--force`。

支持的格式（按代码里的解析分支）：`.md` `.markdown` `.txt` `.csv` `.tsv` `.pdf` `.docx` `.pptx` `.xlsx` `.xlsm` `.html` `.htm`，以及 `.png` `.jpg` `.jpeg` `.bmp` `.webp` `.tif` `.tiff`（走本地 OCR）。

明确不支持、会出现在入库报告里的：音视频（需先转写成文本）、旧版二进制 Office（`.doc` `.xls` `.ppt` 等，请另存为 docx/xlsx/pptx）、压缩包（请先解压）。

扫描版 PDF 和有文字的图片会走 OCR，识别结果带 `ocr_confidence` 元数据（文字是"猜"出来的，检索时应按需降权）。识别不出文字的页面不会伪造空字符串，而是列进入库报告的「读到了但没有可用文本」。

`demo-docs/` 里是 5 篇自造的通用制度文档（员工手册、考勤与请假、差旅与报销、信息安全与数据合规、新员工入职指引），内容与任何真实公司无关，只为让整条链路能跑通。它们是评测集 `eval/eval_set.jsonl` 的对应语料，删掉后评测会失效。

## 技术要点

### ① RRF 融合分的上限很低，它不是相似度

RRF 的公式是 `score = Σ weight / (rrf_k + rank + 1)`，注意分母里加的是 `rank + 1`，而不是得分。默认 `rrf_k = 60`、两路权重都是 1.0，所以：

- 某条片段在两路都排第 1：`1/61 + 1/61 ≈ 0.0328` —— 这已经是理论最高分；
- 只在向量路排第 1：`1/61 ≈ 0.0164`；
- 排到第 6 位：`1/66 ≈ 0.0152`。

也就是说，拿到的融合分基本都在 `0.01 ~ 0.033` 这个区间里。**不要用 0.8 这种量级去判断"相关度够不够"**，`search` 命令输出的 `rrf=0.03` 已经是很好的命中。

这也解释了为什么拒答阈值不能用融合分：融合分只反映"排名"，不反映"有多像"。拒答阈值 `min_top_score` 比的是 `best_dense`（向量余弦，0~1），两者是完全不同的量纲。`rrf_k` 调大只会把整体分数压得更平均，不会改变排序。

选 RRF 而不是「把两路分数归一化后加权求和」，是因为余弦相似度（0~1）和 BM25（0~30+）量纲完全不同，归一化系数还随语料漂移。RRF 只用排名，几乎不需要调参。

接口返回的 `sources[]` 里两个分数字段别混：`score` 就是上面这个融合分（几十位小数那种，只供排序与排查），`dense_score` 才是向量余弦相似度。

还有一点容易误读：**`sources[]` 的排列顺序不是 `dense_score` 的降序**。列表顺序是两路各自排名→RRF 融合→精排之后的结果，余弦相似度只是其中一路的依据。所以实测里问「年假多少天」，第 1 位的 `dense_score` 是 0.5902、第 2 位反而是 0.6709——意思是第 1 位在 BM25 路也排得靠前，融合后名次更高。看到这种「相关度倒挂」不必怀疑算错了。

### ② 为什么要父子块，而不是直接切大块

朴素做法是每 500 字一刀切下去，检索和喂模型用同一批块。它在两个方向上互相矛盾：

- 块切**小**了，向量检索准（语义聚焦），但喂给模型的上下文不完整——问到「请假流程」时给的是流程中的第三步，缺少前提条件，模型只能猜；
- 块切**大**了，上下文完整，但向量是一整段的平均语义，短问题（「年假几天」）很容易被段落里无关内容稀释，召回直接变差。

父子块拆开这两个目标：**父块（≤2200 字）按段落聚合，只作为上下文，不参与检索；子块（≤700 字，重叠 120 字）参与向量与 BM25 检索**。命中子块后，引擎用子块找到父块，把父块喂给模型。

这里有两个容易踩的实现细节，代码里都处理了：

- 同一个父块被多个子块命中时只保留排名最靠前的那一条，否则 6 条命中可能全是同一段话；
- 上下文预算是**按去重后的实际块数**均分的，不是按命中数。6 条命中经常来自 3 个父块，按 6 分每块只拿到 1000 字，而父块上限 2200 字——等于把父块从中间截断，白补了。

顺带一层防护是 `max_per_doc`：同一篇文档最多占 2 条候选。一部长文档切出几十个碎片时，它们的向量分数往往挨得很近，会在截断前把 top_k 全占满，导致最终上下文只剩两三篇文档，答案必然片面。

切分本身是**结构感知**的：以 `#` 标题为天然边界，保留「第三章 考勤管理 > 3.2 请假流程」这样的层级路径，所以引用能精确到小节，而不只是「文档第 8 段」。PDF 会先去掉多页重复的页眉页脚和纯页码，纯文本会用正则识别「第 X 章」「一、」「1.1」这类标题行补上 `#`，让分块器能利用。

## 常见问题

**Q：没配 API Key，或者 Key 填错了，会怎么样？**

服务能正常启动，入库、检索、登录都正常，但回答会变成「离线摘录模式」——直接列出最相关的原文句子并标出处，而不是整合过的答案。引擎在调用失败（含 401）时不会抛 500 给用户，会降级。排查顺序：确认 `.env` 在**项目根目录**（配置层固定读这个位置，不看当前工作目录）；确认 `LLM_API_KEY` 没有引号和多余空格；看日志里是否有 `模型接口返回 401`。若把 `llm.provider` 改成 `extractive`，那是主动选择的离线模式，不会有报错。

**Q：不配 API Key 时，拒答还工作吗？**

**离线摘录模式（`llm.provider: extractive`）不做拒答判定。** 没有 API Key 时系统会自动降级成摘录模式：它只把检索到的最相关原文句子陈列出来，不判断这些片段里是否真的包含答案。因此在这个模式下问「公司有班车吗」这类同域但文档没写的问题，它不会拒答，而是陈列几段看似相关的原文（正文首行会标注当前是离线摘录模式）。内置评测集里的两条负样本，离线模式只拦下跨域那条、同域那条被答了出来（**1/2**）；接上真实模型后是 **3/3** 全拒。这个差距就是"检索有分"和"文档有答案"的区别——前者能算，后者必须读懂。

真正的拒答判定在生成层：接上真实模型后，模型会在无法回答时输出 `NO_ANSWER` 标记，系统据此返回兜底答复。所以**不给 Key 时能验证的是检索与引用链路，不是拒答链路**。在示例语料上用 3 条同域无答案问题（班车 / 食堂几点开饭 / 年终奖怎么算）实测，接入真实模型后全部正确拒答，没有返回无关原文。

同一模式的第二个局限是**挑句**。摘录器按「问题与句子的字面重合度」排序，问法和原文用词差距大时会挑偏：问「报销多久能到账」（作为会话里的第一问），检索已经把写着答案的那一节（报销步骤）排在第 1 位，但摘录器挑出来的是这一节靠前的句子（「出差结束后 15 个工作日内提交报销单」这类），真正回答问题的「审批通过后于次月 15 日随工资打款」因为「打款」和「到账」没有字面重合而被跳过。这是摘录这种启发式方法的固有边界，不是检索故障——检索结果本身是对的。接上模型后由模型通读片段来整合，不受这个限制。

第三个局限是**指代消解**。没有生成能力时，改写这一步整个跳过——问「那它呢」，系统就拿这四个字去检索，不会补全主语。所以离线模式下多轮追问要自己把话说全。接上模型后，含指代词（「这个」「上述」「第 3 步」）或「那…呢」的追问会先做一次改写，规则是**只补主语**：不许引入上一轮回答里的事实、数字、日期，不许把问句改成是非问，超过 40 字也不算数——命中任一条就回退原问题检索。实测把上一答故意写成错数字（45 天 / 10 个工作日），改写结果仍然干净、错数字一个都没进检索串。仍有一种情况不消解：**「第 2 步是什么」这类只带序号的追问**，模型往往原样返回，此时按原句检索。

**Q：第一次 `ingest` 卡在下载模型上，很久没动静。**

首次运行会从 HuggingFace 拉 `jina-embeddings-v2-base-zh` 到 `data/models/`，模型约 640MB，取决于网络。代码默认把端点设为 `https://hf-mirror.com`（`setdefault`，你可以用环境变量覆盖）。Windows 上还主动关了符号链接（`HF_HUB_DISABLE_SYMLINKS=1`），否则没权限建 symlink 时会「下载完成但加载不到模型」。下载完成后完全离线。如果最终降级成了 hash 向量，日志会有 `Embedding provider 'fastembed' 初始化失败…降级为 hash 向量`，此时入库能跑完但召回基本不可用。

**Q：为什么 `data/models/` 占的空间比模型本身大一倍？**

首次运行会下载约 640MB 的 embedding 模型。Windows 上禁用了符号链接（`HF_HUB_DISABLE_SYMLINKS`），同一份模型文件会在 `blobs/` 和 `snapshots/` 各存一份实体拷贝，所以该目录实际占用约 1.2GB。Linux/macOS 上建的是符号链接，不翻倍。

**Q：日志里出现「降级为 hash 向量」，还能继续用吗？**

**不能，把它当停止信号。** 出现这行 WARNING 说明 embedding 模型没加载成功（最常见是内存不足，例如 `[ONNXRuntimeError] Load model… model.onnx failed: bad allocation`），引擎自动换成了 hash 向量：此后所有相似度会掉到接近 0 甚至负数，排序等于随机，**但接口不会报错**——看起来像「检索质量差」，不是「模型没加载」。

所以看到这行日志，**不要看检索结果，也不要先调参数**，先修环境。判断方法：跑一条 `python -m app.cli search "任意问题"`，`best_dense` 接近 0 或为负就是降级了（正常应当是 0.3~0.7 这种量级）。症状也很有特征：服务正常、登录正常，但每条都回「没找到」，很容易被误判成「文档没入库」或「分块不对」，然后去重跑 ingest、换格式、调 `final_top_k`，全是白费功夫。解决内存问题后重启，并清空向量库重新入库（`--reset`），别让 hash 向量留在库里。

**Q：拒答是怎么识别的？换个模型会不会失效？**

拒答的识别依赖模型输出特征：首行 `NO_ANSWER` 标记，或「无引用 + 简述（不超过 160 字）+ 含未提及类措辞」这条兜底启发式。示例语料验证时用的模型走的是后者。

这意味着它有边界：换一个拒答写得更啰嗦、或者在拒答里附了引用的模型，可能被判成正常回答（`citation_missing`）——这类问题仍然会返回兜底答复，但**不会进未答清单**，盲区会在清单里静默消失。改 `app/rag/verdict.py` 的判据之前，先读该文件头部的注释，那里写清了三类判定各自代表什么、哪些该进未答清单。

**Q：管理员初始口令在哪？只看到一次，现在找不到了。**

口令在**账号库第一次被创建**时打印——触发点是第一次提交登录表单（不是打开页面，也不是启动服务）。那一瞬间终端会输出 `[auth] 初始化管理员账号 admin，初始密码：xxxxxxxx（请登录后立即修改）`，密码由 `secrets.token_urlsafe(9)` 随机生成，只打印一次。所以标准操作是：打开页面 → 随便填一次登录（必然失败）→ 回终端抄口令 → 用 `admin` + 该口令登录 → 立刻改密码。

口令丢了就删掉 `data/auth.json` 然后重启服务，会重新生成一个（代价：所有已建账号丢失）。建议改完密码后立刻再建一个管理员账号作为兜底——系统会保护「最后一个启用的管理员」不被停用或降级，避免把自己锁在门外。

**Q：服务起来了，但第一条问题等了很久才出结果。**

**首次请求较慢。** 服务刚启动时第一条 `/chat` 或 `/health` 会多花 5~8 秒（Chroma 加载索引 + fastembed 首次探测模型），此后稳定在 0.2~0.3 秒。这是因为引擎懒加载：进程先就绪、第一个请求到来时才初始化检索组件，所以启动快、第一问慢。

**Q：什么情况下需要重新调整拒答阈值 `min_top_score`？怎么调？**

三种情况必须重标：换语料、换 embedding 模型、换了分块粒度。

标法是准备两批问题——「知识库里确实有答案的」和「明确超出范围的」，两边都用 `python -m app.cli search "问题"` 记录 `best_dense`，看分布。但动手调之前先弄清这个参数能干什么、不能干什么，否则会对着一个调不动的东西反复试。

**它只能挡掉「明显跨域」的问题。** 问天气、问股票、问怎么写代码，这类问题与制度文档的相似度通常不到 0.25，一眼可分。

**它挡不住「同域但文档没写」的问题。** 示例语料上的实测分布：

| 分组 | 题数 | `best_dense` 区间 | 中位 |
|---|---|---|---|
| 库内（文档里有答案） | 15 | 0.3715 ~ 0.7194 | 0.5662 |
| 跨域库外（天气 / 股票 / 写代码） | 10 | 0.0179 ~ 0.2323 | 0.1157 |
| 同域库外（食堂几点开饭 / 有班车吗 / 年会什么时候办） | 5 | 0.1466 ~ **0.4771** | 0.4362 |

注意最后一行：同域库外最高 **0.4771**，高于库内最低 **0.3715**——**两群是重叠的**，不存在能准确分开这两类的阈值。原因不是参数没调好，而是 dense 相似度的固有局限：**它衡量「这段文本和问题像不像」，不衡量「这段文本里有没有答案」**。「公司」「几点」这些词与制度文档高频重合，分数自然被拉高。

**所以有两道防线，阈值只是第一道。** 同域无答案的问题会正常通过检索阈值，由生成层的 `verdict` 判定兜住：模型拿到片段后发现没有依据，输出 `NO_ANSWER`，判定层把这次回答标记为拒答并记进未答清单。`min_top_score` 的定位是**挡掉注定浪费的模型调用**，不是「保证答得对」。

**取值偏向放行。** 默认 `0.30` 在示例语料上能把跨域问题全部挡掉（跨域最高 0.2323 < 0.30）；库内 15 条标定题最低 0.3715，看上去留了 0.07 余量，但**这个余量只对「标定过的问法」成立**——另测 15 条更口语化的库内提问，有 2 条落到 0.29~0.31（「发票抬头写错了行不行」0.2937、「公司电脑能装游戏吗」0.3042），正好卡在门槛上下；其中后者属于「同域但文档没写」，本来就该由第二道防线接住。偏向放行的理由是两种错法的代价不对称：误拒会让用户以为系统坏了或文档没入库，误放行只是模型回一句「没找到」。

这组数字只属于这 5 篇示例文档，换语料照抄会出事——比如按旧经验值 0.48 来卡，会把「收到钓鱼邮件怎么办」（0.3715）和「迟到怎么扣钱」（0.430）这两条本该答得出来的问题挡在门外。

被挡掉的问题都能用 `python -m app.cli unanswered` 看到，这是判断阈值是否过严最直接的证据。设成 0 表示关闭这道闸门，任何问题都会直接进模型。

**Q：既然能调阈值，为什么还会有误放和误拒？**

因为**有些库内问题的分数比跨域问题还低**。示例语料上实测两条：

- 库内、确实有答案的「登录密码忘了」：`best_dense = 0.2901`
- 跨域、该被拒的「上海迪士尼门票多少钱」：`best_dense = 0.3154`

同一件事换个问法分数就变：「密码忘了怎么办」是 0.3416，「密码忘记了」是 0.3036。这道闸门比的不是「该不该答」，而是「字面有多像」，所以不存在能同时解决两边的阈值：降到 0.28 会放行迪士尼，升到 0.32 会挡掉「登录密码忘了」这类本来答得出来的问题。默认取 `0.30`，是往「放行」的方向偏——被放行的同域无答案问题还有生成层判定兜底，而被误拒的问题读者完全拿不到任何线索。**但这不代表 0.30 不会误拒**：上面「登录密码忘了」（0.2901）就在门槛之下，会被第一道闸门挡掉。这类措辞离制度原文较远的提问，要么换一种问法，要么按自己的语料重新标定这个值（标法见上一问）。

示例语料只有 5 篇，这个模糊区间在真实语料下会明显收窄——文档越多、主题越分散，跨域问题与库内片段的相似度越容易拉开。但它不会完全消失，这也是第二道防线必须存在的原因。

**Q：文档明明放进去了，为什么搜不到？**

先看入库报告里三个列表：`格式不支持，未入库`、`读到了但没有可用文本`、错误列表。常见原因：旧版 `.doc`/`.xls` 格式（另存为 docx/xlsx）、扫描版 PDF 没装 OCR 依赖、图片上确实没字、文件在隐藏目录里（扫描会跳过 `.` 开头的路径和 Office 的 `~$` 临时文件）。如果文档在库里但检索不到，用 `search` 看 `dense` 和 `bm25` 分别是什么分：两路都很低说明是问法与文档措辞差距太大，往 `app/rag/glossary.py` 加一组同义词；`bm25` 高但 `dense` 低，说明 embedding 没正常工作。

**Q：通过管理后台改了分类名，但按分类搜不到东西。**

BM25 的索引文本里拼了所属分类名（为了让分类名也能被关键词命中）。分类改名或批量重新归类后，索引里还是旧分类词，所以检索仍走旧词。管理后台有「重建 BM25」动作（`POST /admin/api/bm25/rebuild`），改完分类跑一次即可。入库和删除文档时会自动重建，只有手工改分类这种情况需要手动触发。

**Q：重跑 `ingest` 会不会产生重复数据？**

不会。文档身份优先用内容自带的外部 ID，没有则以「相对路径哈希」为身份；内容哈希一致就直接跳过，同一份文件被复制成多份副本时也只保留一份。mtime 完全一致的文件连读都不读。真正的「更新」是先在同一个批次里删旧向量再写新向量（顺序不能反，反了会把刚写入的新向量一起删掉），并且旧 chunk 的元数据会先被删除——所以中途失败不会出现「新旧两套片段同时被检索到」的情况。

**Q：回答里没有 `[1]` 这种引用编号，或者干脆是空的。**

没有引用编号时，`require_citation` 会给答案补一句「本条回答未标注出处」，这类问题**不会**进未答清单——因为它不是「知识库没有」，而是工程环节（分块或 Prompt）有问题。答案为空最常见的原因是 `llm.max_tokens` 太小，推理模型把预算全花在思考上，正文字段返回空，引擎判定失败后走摘录兜底。

## 开发与测试

```bash
pytest                       # 单元 + 集成测试，用 hash 向量和 memory 后端，不下载模型、不调外部 API
python -m eval.run_eval --ingest ./demo-docs --k 6          # 只评估检索
python -m eval.run_eval --k 6 --answer                       # 同时评估生成（需要配好模型）
python -m eval.run_eval --k 6 --data-dir ./data-eval         # 用独立数据目录，不污染正式库
python -m eval.compare_embedder                              # 对比不同 embedding 的语义召回能力
```

评测脚本在 Recall 低于 80% 时返回非 0，可以直接接 CI。测试用 `provider: hash` + `vector_store: memory`，所以不依赖网络也不依赖模型文件——这也意味着测试通过只说明链路正确，不代表检索质量。
